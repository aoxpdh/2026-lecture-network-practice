# Lab 4 observations

## Task 1
Stop-and-wait를 선택했다. ACK가 유실되면 이미 받은 데이터가 재전송되므로 수신기는 중복 데이터를 다시 붙이지 않고 ACK만 재전송하며, 송신기는 현재 번호와 일치하는 ACK만 인정한다.
2,000바이트는 8바이트씩 최소 250개의 데이터 전송이 필요하다. seed 246에서는 323회(1.292배), seed 999에서는 299회(1.196배) 전송했다. 이 수치는 데이터 채널 전송 시도이며 ACK 채널은 별도다.
처음 작성한 구현은 두 seed 모두 통과해 실제 실패 순서는 관측하지 않았다. 손실에는 타임아웃, 중복·오래된 ACK에는 순서 번호 검사가 필요하며, 다양한 바이트·강한 재정렬·빈 입력도 추가 검증했다.

## Task 2
캡처 권한 부족으로 공식 TCP trace 경로 B를 사용했다. SYN/SYN-ACK/ACK는 1·2·3번이며 ISN은 4236649187·1068969752다. 서로 독립적인 ISN은 과거 연결과의 혼동과 순서 번호 예측을 줄인다. SYN은 MSS 1460, WS 64배, SACK 허용이며 서버 WS는 128배다.
클라이언트 수신 창은 2058×64=131712바이트이고 업로드를 받는 서버는 143번에서 173824바이트를 광고했다. 145번의 최대 in-flight 75296바이트가 이보다 작아 수신 창 포화는 아니며, 시작 단계 혼잡 제어와 짧은 전송의 영향을 추론한다(단일 원인은 확정 불가). trace의 POST 송신자는 192.168.86.68이나 사람의 신원은 알 수 없다.
각 5회 측정한 기존 연결/핫스팟의 중앙값은 77.55/40.78 Mbps, 범위 47.52–174.89/23.35–41.98 Mbps, spread 164.3/45.7%, 연결 시간 중앙값 17.636/33.191 ms였다. 핫스팟은 연결 시간이 길고 처리량이 낮았으며 RTT가 ACK와 slow start를 늦추는 설명과 일치하지만 무선·서버·시간 변화도 섞여 인과관계를 단정하지 않는다.

## Task 3
기준 송신기는 goodput 986.8로 높지만 손실 37.4%, 재전송 2340회, 평균 큐 8.8로 대역폭과 대기 시간을 낭비한다. 구현은 slow start 후 손실 때 창을 0.6배로 줄이고 ACK마다 0.05/window씩 증가시키며 같은 혼잡 묶음의 중복 감소는 ACK 회복 구간으로 억제했다.
이 실행의 최종 창은 약 25.91패킷으로 20패킷의 전파 중 파이프에 소규모 큐를 더한 수준이었다. 계속 증가하는 제어라 영구 수렴값은 아니며 평균 큐 2.25975, 손실 1.863%, goodput 955(기준의 96.78%)로 strong을 충족했다. 다른 RTT나 경쟁 흐름에 대한 보장은 아니다.
감소 계수 0.5에서는 goodput 698.5였고 0.6에서 955로 개선됐다. 더 완만한 0.65는 974.25지만 평균 큐 5.6785로 기준을 초과했다. 0.8도 977.75로 소폭 개선되는 대신 큐 6.67325와 손실 3.172%를 지불했다(bench.txt 참조).
